# Nghia V9.9.0 — Forensic Parity Design

Date: 2026-09-12
Branch: `release-v9.9.0-forensic-parity`
Base: `release-v9.8.1-hold-combo-parity`

## Goal

V9.9.0 narrows the remaining behavior gap between Nghia and the supplied Spotify reference by implementing only behavior supported by Direct or High-structural forensic evidence. It must not invent missing timing, thread topology, detector parameters, or assets.

Scoped parity areas:

1. ONL/disconnect detection and reaction.
2. Auto-sell randomized scheduling.
3. `main_farm_worker` ownership/order reconstruction.
4. Pirate Den and Pirate Den 1 Hit micro-timing/state parity.
5. All Cure external-asset gateway and recovered market workflow readiness.

## Evidence Policy

Every Spotify-derived V9.9 behavior must be recorded in evidence JSON as exactly one of:

- `direct`: literal asset, constant, function/symbol, threshold, coordinate, string, or timing present in the Spotify binary/payload.
- `high_structural`: control/data-flow reconstruction strongly supported by adjacent constants, locals, symbols, call relationships, and prior runtime observations, but not source-identical Python.
- `nghia_fallback`: compatibility or safety behavior added by Nghia and not attributed to Spotify.

High-structural evidence must never be relabeled Direct.

Reference hashes:

- Spotify core executable SHA-256: `6816a9acbf3feb4aa12da996d309844c7335f0fc6726dacbc4b78c94306adbed`
- `main.dll` SHA-256: `62860aeb8a80ac4a768aa8f3afafe23f079aa07e2981786e44989ad71b941cb0`

## Architecture

V9.9 preserves V9.8.1 subsystem boundaries and does not create speculative Spotify threads. Each parity change remains isolated behind an existing module boundary and a shared evidence contract.

### 1. Disconnect / ONL

`spotify_detection_parity.py` gains the recovered ONL detector contract:

- exact asset: `ONL_B64`
- threshold: `0.95` (`direct`)
- watchdog-owned scan path

`spotify_watchdog.py` owns the reaction. On a matched disconnect event:

1. release Nghia-owned inputs;
2. pause farming;
3. emit local alarm/status;
4. use the existing Telegram disconnect path when configured;
5. debounce repeat detections so one persistent disconnect does not spam alerts.

V9.9 does not reconnect, relogin, click login/session UI, or alter Nghia session/license behavior.

The frame/crop path remains `high_structural` unless additional Direct evidence proves a dedicated ROI. V9.9 must not invent one.

### 2. Auto-sell Jitter

`SpotifyWatchdogWorker.get_next_sell_delay()` changes from fixed `minutes * 60` to the recovered High-structural formula:

```python
low_minutes = max(10.0, sell_interval_minutes - 10.0)
high_minutes = sell_interval_minutes * 1.2
delay_seconds = random.uniform(low_minutes, high_minutes) * 60.0
```

Evidence classification:

- `10`, `10`, `max`, `1.2`, `random.uniform`, `60`: `direct`
- operator tree/formula above: `high_structural`

Ownership is explicit:

- **watchdog owns the sell timer and randomized next-delay generation**;
- watchdog raises/records a single pending "sell due" request when the timer matures;
- the main-farm orchestrator may consume that pending request at its recovered sell/safe-place stage, but it must not maintain a second timer or generate a second delay;
- successful sell resets `last_sell_time`, clears the pending request, and generates a new randomized delay;
- disabling auto-sell clears stale delay and pending state;
- scheduling failure never forces a sell action.

### 3. Main Farm Tick Orchestration

V9.9 does not create a new `main_farm_worker` thread. It reconstructs Spotify ownership/order as a tick orchestrator invoked from Nghia's existing farm loop.

Recovered stage order:

1. pause / bot-state gate;
2. consume pending auto-sell / safe-place work;
3. pet stage;
4. lost-player recovery stage;
5. Buff 1 stage;
6. Buff 2 stage;
7. farm-mode dispatch.

Each stage keeps its existing subsystem implementation. The orchestrator owns only ordering, request consumption, and short-circuit decisions. It does **not** duplicate watchdog timers, detector loops, or focus-worker ownership.

Recovered timing/state evidence includes:

- generic loot: base ~90s with `0.9..1.1` jitter (~81..99s);
- pet next interval: `600..800s`;
- pet hold: `500..1000ms`;
- buff press: `600..900ms`;
- buff base: ~120s with recovered jitter constants;
- lost-position staged recovery: approximately `0.1 / 1.5 / 3.0s`;
- fall confirmation: approximately `2.5s`;
- recovery action: `200..600ms`;
- reset delay: `20..40s`;
- floor-jump delay: `90..120s`.

Only timings explicitly classified `direct` or `high_structural` in V9.9 evidence may be used in production code.

Thread start order among watchdog/focus/main farm is not reconstructed. `session_monitor_worker` remains excluded from Nghia.

## Error Handling

V9.9 follows two rules:

- farm/scheduler paths are fail-soft: log the current error, release owned input if necessary, and skip the unsafe action/tick;
- market transactions are fail-closed: any missing evidence, asset-read failure, invalid PNG, detector error, disabled config, or state mismatch blocks clicking.

Pirate input exceptions must release Nghia-owned inputs before returning control to the farm loop.

## Protected Behavior

V9.9 must not change:

- V9.8.1 shared hold-combo semantics for C1/C2/B1/B3;
- MiuMiu image-driven flow except where the orchestrator invokes its already-existing sell path;
- CAPTCHA policy: detection/pause/alert only, no solver/bypass;
- DEAD/revive detector/action contract;
- login/license/session exclusion in Nghia;
- launcher update safety/rollback semantics;
- Dynamic Combo caller status;
- Pirate Laptop scope.

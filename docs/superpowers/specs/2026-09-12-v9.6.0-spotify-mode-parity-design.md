# Nghĩa V9.6.0 — Spotify Mode Parity Design

## 1. Goal

Build V9.6.0 from the current V9.5.0 Focus Parity A branch and bring the remaining farm modes closer to the recovered Spotify behavior without regressing the already-validated C2 path.

The target modes are:

- C1
- C2
- B1
- B3
- Bunny
- C1 (Stand Still)
- Red-Nose Pirate Den 2
- Red-Nose Pirate Den 2 (1 Hit)

V9.6.0 must preserve the current launcher/updater, MiuMiu seller, PC Alarm, user config migration, Focus Parity A, and C2 Fast Worker.

## 2. Source-of-truth hierarchy

When implementation evidence conflicts, use this priority order:

1. Direct Spotify binary evidence and serialized constants.
2. Runtime-validated Spotify video evidence.
3. High-structural reconstruction from Nuitka symbols/locals/constants.
4. Existing Nghĩa behavior only when Spotify evidence is absent.

Do not present high-structural reconstruction as source-identical. Do not invent missing constants.

## 3. Architectural decision

Use one dispatcher with separate mode handlers/state machines rather than one generalized farm loop.

Routing:

- `C1`, `C2`, `B1`, `B3` -> SIMPLE / left-right family.
- `Bunny` -> dedicated Bunny state machine.
- `C1 (Stand Still)` -> dedicated Stand Still state machine.
- `Red-Nose Pirate Den 2` -> dedicated Pirate2 state machine.
- `Red-Nose Pirate Den 2 (1 Hit)` -> dedicated Pirate2-1Hit state machine.

C2 keeps its dedicated Fast Worker and Focus Parity A path. The new handlers must not add window enumeration, focus lookups, full-screen scans, or controller pacing to the C2 hot path.

## 4. Shared runtime rules

### 4.1 Input ownership

Use a single input arbitration boundary so two handlers cannot press conflicting movement/skill keys at the same time. A state transition must release keys owned by the previous state before the next state acts.

### 4.2 Focus

Keep the V9.5.0 dedicated focus worker at approximately 0.2 s cadence. Combat handlers consume cached focus state only.

### 4.3 Safety

On STOP, focus loss fail-safe, unrecoverable state error, or handler generation change:

- release movement keys;
- release flash/teleport key;
- release skill key;
- clear transient mode state;
- do not leave a held key across a restart.

### 4.4 RNG

Preserve recovered timing ranges, but do not attempt to force identical global RNG ordering with Spotify. Windows scheduler jitter, thread interleaving, and game lag are accepted sources of runtime variance.

## 5. SIMPLE family

### 5.1 Map profiles

Use the recovered minimap coordinates:

| Map | LEFT | RIGHT | SAFE_PLACE | Threshold |
|---|---|---|---|---:|
| C1 | (85,169) | (135,169) | (118,160) | 0.6 |
| C2 | (32,169) | (196,169) | (67,161) | 0.6 |
| B1 | (72,168) | (137,168) | (83,153) | 0.6 |
| B3 | (72,168) | (155,168) | (154,160) | 0.6 |

### 5.2 Shared SIMPLE structure

Recovered structural behavior:

- fall confirmation: about 2.5 s;
- release/settle: about 0.01 s;
- fall recovery action: random 200..600 ms;
- approximately 2% long rest branch: uniform 3.0..5.0 s;
- additional human/jump branch up to approximately 8%: 150..300 ms;
- pre-combo sleep: 0.05 s;
- outer hold-combo duration: 200..500 ms.

These values define the SIMPLE family framework. They do not prove that C1/B1/B3 use the exact same inner TP+Skill helper as C2.

### 5.3 C2 protected path

C2 is the runtime-validated mode and must remain unchanged in its core action timing:

- hold current movement direction;
- Teleport/Flash hold: random 20..50 ms;
- Skill hold: random 20..50 ms;
- pair wait: random 0.05..0.15 s;
- repeat while the outer 200..500 ms window remains active;
- preserve PyDirectInput `PAUSE = 0.1` behavior unless a later direct binary finding disproves it.

Do not reduce these delays for subjective speed.

### 5.4 C1/B1/B3 policy

C1/B1/B3 reuse only the recovered SIMPLE movement/edge/fall framework and their own coordinates. Do not automatically force C2 Combo-2 semantics onto these maps.

For B3:

- fixed-Y path is the Spotify-parity path;
- Adaptive Y remains available as a Nghĩa extension through config;
- logs/UI must not label Adaptive Y as source-identical Spotify behavior.

## 6. Bunny state machine

Implement Bunny as a dedicated state machine with these recovered states and constants.

### 6.1 Constants

- recovery left boundary: `x < 25`;
- A: `(55,169)`;
- B trigger: `x >= 147`;
- C: `(139,165)`;
- A return trigger: `x <= 57`;
- B spam duration: about 3.0 s;
- turn-left hold at B: 50 ms;
- spam hold-combo duration: 200..500 ms;
- gap between spam actions: 300..600 ms;
- loop sleep: 0.05 s.

No B_Y constant is invented; B transition is X-driven unless later direct evidence adds Y.

### 6.2 States

`RECOVER_A -> TO_B -> SPAM_B -> TO_C -> TO_A -> TO_B ...`

Behavior:

- `RECOVER_A`: if `x < 25`, move to A `(55,169)`.
- `TO_B`: hold RIGHT until `x >= 147`.
- at B: release movement, press LEFT for 50 ms, enter `SPAM_B`.
- `SPAM_B`: for about 3.0 s, execute skill hold-combos of 200..500 ms with 300..600 ms gaps.
- `TO_C`: move to `(139,165)`.
- `TO_A`: hold LEFT until `x <= 57`; if Y is materially off A, recover using move-to A.

The Bunny handler must not call the SIMPLE left-right handler.

## 7. C1 (Stand Still) state machine

### 7.1 Anchor

On START, capture the current minimap player position as the anchor.

Tolerance:

- X: 3;
- Y: 5.

If drift exceeds tolerance, use move-to anchor. If within tolerance, release movement and execute the primary skill directly.

Do not reuse C2 `hold_combo_action` for normal Stand Still attacking.

### 7.2 Periodic reset

Every random 20..40 s:

- pause 0.5 s;
- alternate LEFT/RIGHT reset direction;
- hold direction 400..1500 ms;
- settle 0.05..0.15 s;
- resume anchor logic.

### 7.3 C1 stand-still loot route

Every random 90..120 s:

- move to `(125,160)`;
- wait 0.3 s;
- DOWN for 100..200 ms;
- wait 0.1 s;
- UP for 300..500 ms;
- wait 0.2 s;
- reacquire the current minimap position and use that observed position as the new anchor before resuming normal Stand Still behavior.

This preserves the recovered reset-anchor behavior without inventing a hidden fixed post-loot coordinate.

## 8. Red-Nose Pirate Den 2 state machine

Pirate2 must remain independent from SIMPLE and from the 1-Hit mode.

### 8.1 Shared Pirate constants

- positional tolerance: 5;
- normal stuck timeout: 2.0 s;
- 1-Hit stuck timeout: 1.5 s;
- bottom loot schedule: base 90 s multiplied by uniform 0.9..1.1, approximately 81..99 s;
- top loot position: `(135,177)`;
- normal top loot interval: 2.5..3.5 min;
- 1-Hit top loot interval: 2.0..2.5 min;
- top return position: `(114,172)`.

### 8.2 Normal farming

Normal Pirate2 farms left/right between profile endpoints.

At either edge:

- release current direction;
- approximately 8% chance of jump/human action 150..300 ms;
- reverse direction;
- wait 0.05 s.

While moving:

- hold movement + skill through the recovered hold-combo action;
- outer hold duration random 200..500 ms;
- do not add an extra controller sleep around the action.

### 8.3 Normal top-loot route

When due:

1. move to `(135,177)` and loot;
2. align to x=134 or x=136 at y=177 according to route direction;
3. hold combo 800..1500 ms;
4. settle 0.2..0.5 s;
5. release movement, ensure LEFT is up, wait 0.05 s;
6. Flash/Teleport 100..150 ms;
7. LEFT down;
8. wait 0.01 s;
9. Skill hold 1000..1500 ms;
10. release LEFT;
11. wait 0.2 s;
12. return to `(114,172)`;
13. wait 0.3 s;
14. settle 200..400 ms;
15. post-settle 2.0..2.5 s;
16. return to FARM with direction RIGHT.

### 8.4 Bottom-loot route

When bottom loot is due:

- if normal Pirate2 is clearly off the farm floor, defer about 5 s so fall recovery can run;
- transition through `LOOTING_BOT_1 -> LOOTING_SWEEP -> LOOTING_BOT_2`;
- loot key short press: 100..150 ms;
- downward settle: 0.5..0.8 s;
- one-time sweep skill hold: 1.6 s normal;
- generic loot combo hold: 200..500 ms;
- sweep tolerance: 6;
- BOT2 completion tolerance: 10;
- sweep settle: 0.1..0.3 s;
- normal mode alternates sweep direction using its own `curr_loot_dir` state.

## 9. Red-Nose Pirate Den 2 (1 Hit) state machine

1-Hit must not reuse the normal Pirate continuous combat worker.

### 9.1 Farm states

`MOVE_RIGHT -> RIGHT_SETUP -> HIT_RIGHT -> MOVE_LEFT -> LEFT_WAIT -> HIT_LEFT -> MOVE_RIGHT ...`

Recovered behavior:

- move RIGHT to right edge;
- move-to/setup target `(178,183)`;
- wait random 300..1500 ms;
- execute exactly one direct primary skill action;
- move LEFT;
- at left edge wait exactly 1.5 s;
- execute exactly one direct primary skill action;
- move RIGHT;
- repeat.

No continuous primary-skill spam is allowed in this mode.

### 9.2 1-Hit top-loot route

When due:

1. move to `(135,177)`;
2. release and face LEFT;
3. wait 0.05 s;
4. loot key 100..150 ms;
5. wait 0.2 s;
6. return to `(114,172)`;
7. settle 200..400 ms;
8. schedule next top loot for 2.0..2.5 min;
9. return to FARM with the recovered 1-Hit movement state.

### 9.3 1-Hit bottom-loot route

Use the same bottom-loot state sequence, but:

- fixed LEFT sweep direction;
- one-time sweep skill hold: 1.5 s;
- do not use normal Pirate `curr_loot_dir` alternation.

## 10. Integration boundaries

Primary implementation should stay inside the behavior layer and the minimum host bridges needed to expose config/state.

Expected touched files:

- `spotify_behavior_engine.py` or a new focused mode module imported by it;
- `spotify_recovered_core.py` if constants/state helpers belong there;
- `maple_nghia_pro.py` only for profile/config/host bridges and minimal logging;
- tests for dispatch and each mode state machine;
- release patch/payload metadata for V9.6.0.

Do not refactor launcher/updater code as part of this change.

## 11. Testing strategy

### 11.1 Dispatcher tests

Assert exactly one handler family per profile:

- C1/C2/B1/B3 -> SIMPLE;
- Bunny -> Bunny;
- C1 (Stand Still) -> Stand Still;
- Pirate2 -> Pirate2;
- Pirate2 1 Hit -> Pirate2-1Hit.

### 11.2 Timing-range tests

Use deterministic RNG injection/fakes to verify generated durations remain inside recovered ranges. Tests should check bounds, not exact random samples.

### 11.3 State-transition tests

For each dedicated state machine, feed synthetic minimap positions and monotonic timestamps and assert:

- next state;
- intended direction;
- expected action count;
- no conflicting held keys;
- scheduled timer updates.

### 11.4 1-Hit invariant

Assert one skill action per edge hit state and no continuous skill loop.

### 11.5 Stand Still invariant

Assert skill-direct path while inside anchor tolerance and movement recovery only outside tolerance.

### 11.6 C2 non-regression

Assert the C2 helper still uses:

- Teleport 20..50 ms;
- Skill 20..50 ms;
- pair wait 0.05..0.15 s;
- outer 200..500 ms;
- cached focus path only.

No new full-window lookup is allowed inside a C2 combat tick.

### 11.7 Stop/restart safety

For every mode, STOP/restart/generation change must release all owned keys and reset transient state.

## 12. Release strategy

Create V9.6.0 on a branch derived from `release-v9.5.0-focus-parity`.

Release requirements:

- preserve user config and updater contract;
- keep Focus Parity A default behavior;
- retain MiuMiu and PC Alarm unchanged;
- publish V9.6.0 portable/update assets through the existing GitHub Actions release flow;
- update release notes to distinguish runtime-validated C2 from high-structural parity modes.

Do not overwrite or mutate the V9.5.0 release.

## 13. Acceptance criteria

V9.6.0 is acceptable when all of the following hold:

1. C2 tests prove no timing/focus-path regression.
2. Bunny, Stand Still, Pirate2, and Pirate2-1Hit dispatch to dedicated handlers.
3. Pirate2 normal and 1-Hit never share continuous attack semantics.
4. Stand Still does not use C2 hold-combo attack behavior.
5. Bunny follows A -> B -> spam -> C -> A state order.
6. SIMPLE maps retain their own coordinates and recovered edge/fall behavior.
7. B3 Adaptive Y remains explicitly labeled as a Nghĩa extension.
8. STOP/restart releases all inputs for every mode.
9. Existing launcher/updater, MiuMiu, PC Alarm, config migration, and Focus Parity A tests continue to pass.
10. GitHub Actions can build the V9.6.0 release artifacts successfully.

## 14. Out of scope

- claiming exact source recovery from Nuitka;
- inventing missing Spotify constants;
- changing C2 delays for subjective speed;
- redesigning the UI;
- changing MiuMiu seller behavior;
- changing PC Alarm behavior;
- replacing the updater architecture;
- guaranteeing identical Windows scheduler jitter, RNG interleaving, or network/game-lag behavior.

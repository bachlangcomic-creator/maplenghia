# Nghĩa V9.7.0 — Spotify Detection & Watchdog Parity Design

## 1. Goal

Build V9.7.0 from the released V9.6.0 Spotify Mode Parity line and recover the next highest-confidence Spotify subsystems that remain incomplete in Nghĩa:

1. safe-place verification before sell/recovery actions;
2. Spotify-specific detection contracts for CAPTCHA and full-bag detection;
3. watchdog worker topology;
4. evidence-gated session-monitor and dynamic-combo recovery work.

V9.7.0 must preserve the V9.6.0 farm-mode behavior, C2 timing/focus path, MiuMiu seller flow, PC Alarm, updater, launcher, config migration, and input fail-safe behavior.

The release must not claim source-identical parity where only high-structural evidence exists.

## 2. Source-of-truth hierarchy

When implementation choices conflict, use this order:

1. direct Spotify binary/payload evidence;
2. runtime-validated Spotify behavior;
3. high-structural reconstruction from Nuitka names, locals, constants, strings, and call ordering;
4. current Nghĩa behavior only as a labeled fallback when Spotify evidence is incomplete.

Rules:

- Do not invent missing constants.
- Do not reuse a Nghĩa template or threshold and label it as Spotify parity unless the Spotify source asset/logic is recovered.
- Do not infer `session_monitor_worker` semantics from its name alone.
- Do not connect reconstructed dynamic-combo helpers to farm modes until caller mapping is supported by evidence.

## 3. Baseline and protected behavior

V9.7.0 is based on V9.6.0.

Protected behavior that must not regress:

- C2 Teleport/Skill ordering and timing;
- C2 cached-HWND/focus-worker architecture;
- SIMPLE C1/C2/B1/B3 mode routing;
- Bunny dedicated state machine;
- Stand Still direct-skill behavior;
- Pirate2 normal and 1-Hit separation;
- B3 fixed-Y Spotify-parity default;
- MiuMiu image-driven seller;
- PC Alarm 2000 Hz / 300 ms behavior;
- updater/launcher release contract;
- STOP/restart input release safety.

No V9.7 detector or watchdog change may add full-screen scanning, window enumeration, blocking network work, or controller sleeps to the C2 hot path.

- minimap monitor: 300×250;
- CAPTCHA ROI: top 200, left 300, width 650, height 350;
- `CAPTCHA_THRESHOLD = 0.70`;

### 4.2 Safe-place behavior

High-structural evidence indicates:

- move to configured safe place;
- settle for approximately 1.0 s;
- verify safe-place arrival up to 6 times before continuing.

The available evidence does not establish a new independent positional tolerance for this verification. V9.7 therefore reuses the already-recovered movement/arrival tolerance rather than inventing a new number.

### 4.3 Worker topology

Direct worker symbols exist for:

- `watchdog_worker`;
- `session_monitor_worker`;
- `focus_enforcer_worker`;
- `main_farm_worker`.

V9.6 already recovered the dedicated focus-worker architecture sufficiently for current purposes. V9.7 adds a watchdog worker boundary while keeping session-monitor semantics evidence-gated.

### 4.4 Alarm behavior

Spotify watchdog/alarm evidence includes:

- `winsound.Beep`;
- 2000 Hz;
- 300 ms;
- CAPTCHA local alarm repeat count 3.

V9.7 must preserve the existing Spotify PC Alarm parity implementation rather than replace it.

## 5. Architectural decision

Add a detector/watchdog layer beside the behavior engine instead of expanding the C2/farm hot path.

Expected runtime topology:

```text
focus worker (~0.2 s)
    -> owns focus/HWND refresh

farm worker(s)
    -> consume cached focus state
    -> movement/combat only

watchdog worker
    -> captures/receives alert frame data
    -> runs CAPTCHA / dead / disconnect / full-bag alert checks
    -> emits alert events

MiuMiu/sell flow
    -> consumes full-bag event
    -> moves to safe place
    -> requires safe-place verification
    -> performs existing image-driven sell state machine

session monitor
    -> no new runtime semantics until direct/high-structural evidence is sufficient
```

Detection logic must be isolated from movement logic and independently testable.

## 6. New detection-parity module

Create a focused module, expected name:

`spotify_detection_parity.py`

Responsibilities:

- define Spotify detector constants and ROI contracts;
- crop detector ROIs from a captured game frame;
- expose deterministic template-match helpers;
- clearly distinguish `spotify_exact`, `spotify_structural`, and `nghia_fallback` detector sources;
- never own alert side effects directly;
- never press keys or move the mouse.

Suggested result type:

```python
@dataclass(frozen=True)
class SpotifyDetectionResult:
    kind: str
    matched: bool
    score: float | None
    threshold: float | None
    source: str
```

Allowed `source` values:

- `spotify_exact` — exact Spotify asset/logic recovered;
- `spotify_structural` — structure/threshold/ROI recovered but exact source asset still uncertain;
- `nghia_fallback` — existing Nghĩa detector retained for compatibility.

Logs/UI must not collapse these categories into one generic "Spotify" label.

## 7. CAPTCHA detector design

### 7.1 ROI

Use the recovered Spotify CAPTCHA ROI relative to the 1280×720 game client:

- left = 300;
- top = 200;
- width = 650;
- height = 350.

If the active game client is not 1280×720, V9.7 must not silently stretch the ROI and claim exact parity. It may either:

- use the current Nghĩa fallback path; or
- use an explicitly labeled scaled fallback if one already exists.

### 7.2 Thresholds

Recovered thresholds:

- primary: 0.70;
- secondary: approximately 0.68.

The second threshold may be used only with the corresponding recovered detector/template path. Do not apply `0.68` to an unrelated user-supplied template simply because the constant exists.

### 7.3 Asset gating

If the exact Spotify CAPTCHA template assets are not available from the current raw binary/payload evidence, V9.7 must not fabricate them.

In that case:

- the Spotify ROI/threshold contract is implemented and tested;
- existing Nghĩa CAPTCHA detection remains available as `nghia_fallback`;
- logs state that exact Spotify CAPTCHA asset parity is still pending.

### 7.4 Alert path

On a CAPTCHA match:

- emit a watchdog alert event;
- preserve existing pause-on-alert behavior;
- preserve PC Alarm parity, including local repeat semantics where already implemented;
- do not run alarm logic inside the detector function itself.

## 8. Full-bag detector design

### 8.1 Threshold

Use direct recovered constant:

`FULL_BAG_DETECT_THRESHOLD = 0.35`.

### 8.2 Asset gating

The threshold alone is insufficient to prove full detector parity. Exact Spotify full-bag asset/crop logic must be recovered before a detector is labeled `spotify_exact`.

Until then:

- preserve the existing Nghĩa full-bag trigger as `nghia_fallback`;
- add a structural Spotify detector interface using the recovered threshold only when paired with a recovered/validated asset path;
- do not replace a working Nghĩa trigger with an unvalidated structural guess.

### 8.3 Sell trigger contract

A full-bag event may request MiuMiu auto-sell, but auto-sell cannot begin until safe-place verification succeeds.

The sell trigger contract is:

```text
FULL_BAG event
-> pause/serialize farm inputs
-> move to configured safe place
-> settle
-> verify safe place
-> only then enter existing MiuMiu seller
```

If verification fails, the seller must not start.

## 9. Safe-place verification state machine

Extend the recovered core safe-place path with explicit verification state.

Suggested states:

`MOVE_SAFE -> SETTLE_SAFE -> VERIFY_SAFE -> SAFE_OK | SAFE_FAIL`

### 9.1 MOVE_SAFE

Use the existing safe-place coordinates from the active map profile and the existing movement helper.

Do not introduce a new movement algorithm.

### 9.2 SETTLE_SAFE

After arrival, settle for approximately 1.0 s using the recovered value.

### 9.3 VERIFY_SAFE

Perform up to 6 verification attempts.

Each attempt:

- consumes the latest valid minimap/player observation;
- checks safe-place arrival using the existing recovered move-to/arrival tolerance;
- succeeds immediately if the observation is valid and within tolerance;
- fails closed if no valid observation is available after all attempts.

Do not invent an extra inter-attempt sleep constant. Verification proceeds at the surrounding worker/tick cadence unless later direct evidence supplies a distinct delay.

### 9.4 SAFE_OK

Only after verification succeeds may the caller continue into auto-sell or other safe-place-dependent actions.

### 9.5 SAFE_FAIL

On failure:

- release owned movement/skill inputs;
- do not start MiuMiu selling;
- return control to recovery/farm logic according to existing generation/state rules;
- log the failure as a parity-safe abort rather than silently continuing.

## 10. Watchdog worker design

Introduce a dedicated watchdog worker boundary consistent with the Spotify topology.

Responsibilities:

- execute alert/detection work outside farm hot paths;
- maintain its own generation/stop lifecycle;
- consume captured frame data or perform its own capture without blocking C2;
- emit typed alert events;
- call existing alert response bridges rather than duplicating alarm/Telegram logic.

Initial event kinds may include existing Nghĩa-supported alerts such as:

- CAPTCHA;
- dead;
- disconnect;
- full bag.

However, only the worker topology is claimed as Spotify parity where direct evidence supports it. Existing Nghĩa detector semantics remain labeled as fallbacks unless separately recovered.

The watchdog worker must not:

- directly press combat keys;
- own focus/HWND refresh;
- modify C2 timing constants;
- call MiuMiu seller without going through the safe-place gate;
- perform long blocking work while holding the shared input lock.

## 11. Session-monitor policy

`session_monitor_worker` is direct binary evidence, but its internal responsibility is not sufficiently recovered.

V9.7 policy:

- do not infer login, license, network, account, or session-expiry semantics from the name;
- do not create a fake runtime worker that claims Spotify behavior while doing nothing meaningful;
- document the symbol and preserve a future integration boundary;
- only implement active behavior after additional raw-binary call-graph evidence is recovered.

This subsystem is explicitly evidence-gated and may remain unimplemented in V9.7 without failing acceptance criteria.

## 12. Dynamic-combo policy

Reconstructed dynamic combo helpers/timing catalogs may exist in Nghĩa, but current evidence does not establish the exact caller mapping for FOCUS/SPAM/LAZY/default combo variants.

V9.7 must therefore:

- leave those helpers dormant unless they already serve a validated path;
- add no new UI toggle that routes arbitrary maps into these combos;
- add static tests proving C2 still uses its validated TP+Skill path;
- record caller-mapping recovery as future forensic work.

No farm mode may be changed to a different combo profile solely because the helper exists.

## 13. Main-farm worker policy

Spotify contains a dedicated `main_farm_worker`, but V9.6 already has working mode dispatch and a protected C2 worker.

V9.7 does not perform a broad farm-thread rewrite.

Reason:

- watchdog/detection recovery is the current scope;
- changing all farm scheduling at the same time would make runtime regressions harder to attribute;
- exact global RNG/thread interleaving cannot be guaranteed anyway.

The existing mode dispatcher remains intact. Worker-topology work in V9.7 is limited to the watchdog boundary.

## 14. Input ownership and concurrency

All existing single-owner input guarantees remain in force.

Rules:

- detector code never acquires persistent input ownership;
- watchdog event handling may request farm pause/release through existing behavior-engine APIs;
- safe-place movement uses the same serialized input boundary as the current farm/recovery code;
- MiuMiu may start only after farm input ownership is released and safe-place verification succeeds;
- STOP/generation change must terminate watchdog work and release farm-owned inputs;
- alert handling must not deadlock with focus worker or MiuMiu worker.

## 15. Configuration and compatibility

V9.7 must preserve existing user config.

New config should be minimal and migration-safe.

Possible internal keys:

- `spotify_watchdog_parity_enabled` — default true only if the worker uses current safe behavior;
- `spotify_detection_source` — internal status/reporting, not necessarily a user-facing toggle;
- migration marker for V9.7 detector/watchdog setup.

Do not expose raw evidence labels as confusing UI switches unless necessary. Prefer logs/status text over new controls.

Existing Nghĩa alert templates/settings remain compatible.

## 17. Testing strategy

### 17.1 Baseline regression

Run all V9.6 parity tests unchanged before and after V9.7 patches.

### 17.2 Detector constant tests

Assert:

- CAPTCHA ROI = `(300, 200, 650, 350)` in left/top/width/height semantics;
- primary CAPTCHA threshold = `0.70`;
- secondary CAPTCHA threshold is approximately `0.68` only on its intended detector path;
- full-bag threshold = `0.35`;
- seller threshold remains `0.65` and is not confused with full-bag threshold.

### 17.3 Detector source-label tests

Assert a fallback detector cannot return `source="spotify_exact"`.

### 17.4 Safe-place tests

Use deterministic fake observations to verify:

- settle occurs before verification;
- verification succeeds early when within tolerance;
- maximum 6 attempts;
- six failed observations produce `SAFE_FAIL`;
- MiuMiu is not entered on failure;
- no new positional tolerance constant is invented.

### 17.5 Watchdog lifecycle tests

Assert:

- watchdog has independent start/stop generation;
- watchdog stop terminates cleanly;
- alert emission does not press combat keys;
- C2 hot path does not call watchdog detector functions synchronously;
- focus/HWND lookup remains owned by Focus Parity A.

### 17.6 Full-bag -> sell integration

Assert:

```text
full-bag event
-> farm release/pause
-> safe-place movement
-> 1.0 s settle
-> <=6 verify attempts
-> MiuMiu only if verified
```

### 17.7 C2 non-regression

Assert no change to:

- TP hold 20..50 ms;
- Skill hold 20..50 ms;
- pair wait 0.05..0.15 s;
- outer 200..500 ms;
- cached focus/HWND path.

### 17.8 Packaging regression

Hash-gate unchanged protected files where practical and retain real Windows launcher smoke tests in release CI.

## 18. Failure behavior

V9.7 favors fail-closed behavior for parity-sensitive automation.

Examples:

- unknown detector asset -> use labeled Nghĩa fallback or no parity claim;
- safe-place verification failure -> abort sell;
- capture failure -> no positive detection event;
- watchdog exception -> release/pause only through existing safe host bridge, log error, do not crash C2 worker;
- missing session-monitor evidence -> no invented behavior.

## 20. Acceptance criteria

V9.7.0 is acceptable when all of the following hold:

1. All V9.6 farm-mode regression tests still pass.
2. C2 timing/focus hot path is unchanged.
3. Safe-place flow performs 1.0 s settle plus at most 6 verification attempts.
4. Auto-sell cannot start after failed safe-place verification.
5. CAPTCHA detector contract uses the recovered Spotify ROI and threshold values without falsely labeling fallback templates as exact parity.
6. Full-bag detector contract preserves the direct `0.35` threshold and distinguishes it from seller threshold `0.65`.
7. A dedicated watchdog worker boundary exists and alert detection is not run synchronously in the C2 combat hot path.
8. Existing MiuMiu seller behavior remains unchanged after the safe-place gate.
9. Existing PC Alarm behavior remains unchanged.
10. `session_monitor_worker` receives no invented semantics without new evidence.
11. Dynamic combo helpers are not newly wired to farm modes without caller evidence.
12. STOP/restart/focus-loss safety still releases inputs.
13. GitHub Actions can build and verify V9.7.0 artifacts successfully.
14. Release notes distinguish exact/direct evidence, high-structural recovery, and Nghĩa fallback behavior.

# Nghĩa V9.8.0 — Exact Detector & Watchdog Recovery Design

## 1. Goal

Build V9.8.0 from the released V9.7.0 Detection & Watchdog Parity line and replace the highest-confidence detector/watchdog fallbacks with evidence recovered directly from the raw Spotify Offline NoLogin binary payload.

V9.8.0 focuses on four areas:

1. exact Spotify detector assets and detector contracts for CAPTCHA, dead/revive, disconnect/online, and inventory-full states;
2. a broader Spotify watchdog responsibility set, while keeping detector work outside all farm hot paths;
3. evidence-backed session-monitor behavior;
4. evidence-backed sell scheduling ownership, with no invented jitter constants.

The release must preserve the V9.7.0 farm/combat behavior, especially C2 timing/focus, existing MiuMiu seller behavior, PC Alarm, launcher/updater, safe-place sell gate, and STOP/restart input-release guarantees.

V9.8.0 must never claim source-identical or exact Spotify behavior where only structural evidence is available.

## 3. Source-of-truth hierarchy

When evidence conflicts, implementation follows this order:

1. direct bytes/symbols/constants/call-site evidence from the supplied Spotify binary/payload;
2. runtime-validated Spotify behavior;
3. high-structural reconstruction from Nuitka constants, locals, names, and surrounding call ordering;
4. V9.7 Nghĩa behavior as a clearly labeled fallback.

Rules:

- exact recovered bytes may be labeled `spotify_exact`;
- recovered thresholds/flow without complete call geometry are `spotify_structural`;
- V9.7 user-template behavior remains `nghia_fallback`;
- a structural detector/action cannot be promoted to exact merely because it uses an exact asset;
- unknown click coordinates, timing bounds, retry delays, scheduler cadences, or caller mappings must not be invented.

## 6. Detector architecture

`spotify_detection_parity.py` remains the detector-policy layer and is extended rather than replaced.

Required result contract remains:

```python
@dataclass(frozen=True)
class SpotifyDetectionResult:
    kind: str
    matched: bool
    score: float | None
    threshold: float | None
    source: str
```

Allowed sources:

- `spotify_exact`
- `spotify_structural`
- `nghia_fallback`

V9.8 adds detector-path metadata internally where useful, but source labels remain stable for compatibility.

Detector functions must be deterministic for a supplied frame and must not:

- pause the bot;
- play alarms;
- send Telegram messages;
- press keys;
- move/click the mouse;
- enumerate windows;
- call session/network APIs.

All side effects stay in watchdog/host bridges.

## 7. CAPTCHA recovery

### 7.1 Direct evidence

Recovered direct constants/paths:

- game size: 1280×720;
- CAPTCHA ROI: left `300`, top `200`, width `650`, height `350`;
- primary threshold: `0.70`;
- second CAPTCHA threshold: approximately `0.68` on the corresponding second detector path;
- exact assets: `LIE_B64`, `QUESTION_CAPTCHA_1_B64`, `QUESTION_CAPTCHA_2_B64`;
- worker ownership: watchdog;
- Spotify binary also contains `process_auto_captcha` and Gemini-related logic.

### 7.2 V9.8 policy

V9.8 implements exact detection for the recovered CAPTCHA assets/ROI/threshold paths where call-site evidence is sufficient.

For a 1280×720 game frame:

- use the exact ROI contract;
- primary Lie Detector matching may report `spotify_exact` only when using exact `LIE_B64` and recovered threshold semantics;
- Question CAPTCHA assets may report `spotify_exact` only on their recovered matching path;
- do not apply the secondary threshold to unrelated templates.

For non-1280×720 frames:

- exact Spotify CAPTCHA path is disabled;
- an existing Nghĩa fallback may continue as `nghia_fallback`;
- scaled ROI logic must not be labeled exact.

### 7.3 Strict no-solver invariant

V9.8 must **not** implement Spotify's Gemini/AI auto-CAPTCHA solver.

On any CAPTCHA match, allowed behavior is only:

`detect -> pause/release farm input -> alarm/Telegram -> wait for user`

Prohibited in V9.8:

- sending CAPTCHA images to Gemini or another model to solve them;
- generating an answer to the challenge;
- clicking/typing a CAPTCHA solution;
- retrying or bypassing the challenge automatically.

Tests must fail if a CAPTCHA detector/watchdog path imports or calls Gemini/Google generative AI APIs.

## 8. Full-bag detector recovery

Direct evidence:

- `FULL_BAG_DETECT_THRESHOLD = 0.35`;
- `INV_FULL_B64`;
- `INV_FULL_2_B64`;
- `INV_FULL_KOREA_B64`;
- `detect_image_canny_edge` appears in the watchdog/full-bag cluster;
- seller threshold remains separately `SELL_THRESHOLD = 0.65`.

V9.8 must implement a multi-variant full-bag detector that preserves these distinctions.

Required behavior:

- exact recovered inventory-full assets are tried only through recovered image/canny paths;
- threshold `0.35` is never reused as MiuMiu seller threshold;
- detector result identifies which variant/path matched for diagnostics;
- full-bag detection emits a sell request event, but cannot directly invoke MiuMiu;
- V9.7 safe-place verification remains mandatory before seller entry.

If exact crop geometry for a specific asset cannot be recovered, that variant is `spotify_structural` until validated; V9.8 must not fabricate a crop rectangle.

## 9. Dead/revive recovery

Direct evidence includes:

- exact `DEAD_B64`;
- watchdog dead-detection strings;
- PyDirectInput mouse movement/click primitives in the dead branch;
- a user-visible branch equivalent to clicking "Hồi sinh";
- Telegram dead notification strings.

V9.8 separates **dead detection parity** from **revive action parity**.

### 9.1 Detection

Matching exact `DEAD_B64` through the recovered detector path may be labeled `spotify_exact`.

### 9.2 Revive action

A new watchdog event, expected logical name `REVIVE_REQUIRED`, is emitted on an exact dead match.

The host may perform auto-revive only when the action target/call geometry is supported by recovered evidence or an already-existing validated host action. If exact click coordinates/target geometry are still unavailable, V9.8 must:

- pause/release;
- alert;
- expose `REVIVE_REQUIRED`;
- **not invent a click position**.

Therefore the V9.8 release may contain exact dead detection even if auto-revive action remains structural/fallback.

Any enabled auto-revive implementation must be isolated from combat input ownership and never execute while farm movement/skill keys remain held.

## 10. Disconnect/online detector recovery

Direct evidence includes:

- exact `ONL_B64`;
- watchdog disconnect strings;
- `detect_image` association in the same branch cluster;
- Telegram disconnect notification path.

V9.8 adds an exact/structural Spotify disconnect detector according to the recovered image path.

On match:

- emit a typed disconnect event;
- release/pause farm input;
- preserve existing alarm/Telegram bridges;
- never attempt credential re-login or network bypass from watchdog.

The detector must not be confused with `session_monitor_worker`; disconnect image detection and account/session validity are separate responsibilities.

## 11. SpotifyWatchdogWorker V9.8 responsibilities

`SpotifyWatchdogWorker` remains the dedicated watchdog object introduced in V9.7 and expands its evidence-backed responsibilities.

It owns:

- alert frame capture through the existing host capture bridge;
- exact/fallback CAPTCHA checks;
- dead detection;
- disconnect detection;
- full-bag detection;
- event emission;
- local alarm/Telegram request routing through existing host response bridges;
- sell scheduling ownership;
- coordination with safe-place sell requests.

It must not:

- enumerate windows in the loop;
- call `_find_game_window`/`EnumWindows` in the loop;
- refresh focus ownership;
- inject combat keys;
- run detector work inside C2 Fast Worker;
- execute MiuMiu before safe-place `READY`;
- solve CAPTCHA;
- perform blocking session/network checks while holding shared input locks.

Watchdog continues to consume cached HWND/focus state only.

## 12. Sell scheduling recovery

Direct evidence now establishes that Spotify watchdog owns:

- `last_sell_time`;
- `next_sell_delay`;
- `sell_interval_minutes`;
- `get_next_sell_delay`;
- `random.uniform` usage.

This is enough to recover scheduling ownership and randomized-delay structure, but the currently recovered evidence does **not** establish the exact `random.uniform` bounds.

V9.8 therefore must not invent jitter bounds.

Required implementation policy:

- move sell-timer ownership into watchdog if V9.7 still owns it elsewhere;
- introduce a testable `get_next_sell_delay` boundary;
- preserve the configured `sell_interval_minutes` meaning;
- if exact jitter bounds are recovered during implementation from raw binary evidence, amend this spec before activating them as Spotify exact;
- otherwise keep V9.7 timing behavior as `nghia_fallback` while logging that watchdog ownership is recovered but jitter constants remain pending.

This prevents a guessed randomized timer from being mislabeled Spotify parity.

## 13. Safe-place + MiuMiu contract remains unchanged

V9.8 must preserve the V9.7 sell gate:

`FULL_BAG/TIMER SELL REQUEST -> pause/serialize farm -> MOVE_SAFE -> SETTLE_SAFE -> VERIFY_SAFE -> READY -> MiuMiu`

If the safe gate returns `FAILED`:

- clear/abort the sell request according to V9.7 behavior;
- release owned movement/skill inputs;
- do not enter MiuMiu;
- return to recovery/farm under existing generation rules.

MiuMiu seller core is protected. Detector/watchdog work must not rewrite its image-driven steps.

## 14. Session monitor recovery

New binary evidence is sufficient to recover the **basic semantic contract** of `session_monitor_worker`.

Direct/high-structural chain:

`username -> session_token -> check_session -> invalid/KICK -> disable_all_controls`

V9.8 may therefore add a dedicated `SpotifySessionMonitorWorker` or equivalent worker boundary.

Responsibilities:

- read the currently active username/session token from the host/session bridge;
- call the existing/recovered `check_session` bridge outside input locks;
- on valid session, remain passive;
- on invalid/kicked session:
  - stop/pause farm generation;
  - release owned inputs;
  - emit a session-invalid event;
  - disable controls through a host bridge equivalent to `disable_all_controls`;
  - log the evidence source.

V9.8 must not invent:

- new license schemes;
- machine/HWID enforcement;
- credential validation rules;
- retry/backoff timing not recovered;
- automatic login/re-authentication behavior.

The Spotify Offline NoLogin wrapper's local auth behavior is external scaffolding and must not be treated as farm-engine evidence.

If the current Nghĩa runtime has no compatible `check_session` source, the worker may be implemented behind a host bridge and disabled/passive for NoLogin builds rather than fabricating server semantics.

## 15. Dynamic-combo policy

Binary evidence confirms the existence of:

- `perform_dynamic_combo`;
- FOCUS;
- SPAM;
- LAZY;
- default/dynamic variants.

However exact caller mapping from farm modes/configs remains insufficiently proven.

V9.8 policy is unchanged from V9.7:

- do not wire new callers;
- do not add a UI mode switch;
- do not route C2 into dynamic combo;
- preserve the validated static C2 TP+Skill path;
- continue forensic recovery separately.

Static tests must continue proving no new dynamic-combo caller appears.

## 16. `main_farm_worker` policy

Spotify contains `main_farm_worker`, but V9.8 does not perform a global farm-thread rewrite.

Reason:

- detector/watchdog/session recovery is independently testable;
- V9.7 farm paths are already stable;
- changing global worker scheduling at the same time would make timing regressions difficult to attribute;
- exact thread/RNG interleaving remains unrecoverable from static Nuitka evidence alone.

Existing Nghĩa mode dispatch and C2 Fast Worker remain intact.

## 17. Auto Market All Cure scope

Binary evidence confirms a separate subsystem:

- `buy_all_cure_loop`;
- `sell_all_cure_loop`;
- market/shop UI flow;
- test hotkeys including F3/F7;
- All Cure purchase/listing behavior.

This subsystem is **explicitly out of V9.8 scope**.

Reason:

- it is functionally independent from detector/watchdog/session recovery;
- it has separate NPC/market UI state, input ownership, and failure handling;
- combining it with V9.8 would broaden regression surface unnecessarily.

Target it as a future V9.9 design after V9.8 detector/watchdog/session behavior is stable.

## 18. Input ownership and concurrency

Single-owner input guarantees remain mandatory.

Rules:

- detector code owns no input;
- watchdog may request release/pause through host/behavior bridges;
- dead/revive action cannot overlap farm key ownership;
- session invalidation must release farm input before controls are disabled;
- MiuMiu may run only after safe-place verification and farm-input release;
- focus worker remains the only focus/HWND refresh owner;
- watchdog and session workers must stop on generation change/STOP;
- no long network/image processing while holding shared input locks;
- C2 Fast Worker remains free of watchdog/session calls.

## 19. Configuration and compatibility

V9.8 preserves all existing user config.

Migration-safe additions may include:

- `spotify_exact_detector_v1`: boolean migration marker;
- `spotify_session_monitor_enabled`: boolean, default chosen to preserve NoLogin compatibility;
- `spotify_auto_revive_enabled`: boolean only if action parity is sufficiently recovered;
- `spotify_watchdog_parity_v2`: migration marker.

Rules:

- exact/structural/fallback source is runtime evidence status, not a user preference;
- no config migration may erase V9.7 templates, map profiles, hotkeys, Telegram settings, or updater state;
- user-supplied detector templates remain usable as fallback where exact Spotify path is unavailable.

## 21. Testing strategy

V9.8 uses TDD for every production behavior change.

### 21.1 Baseline regression

Before production changes, all V9.7 tests must pass on the exact V9.7 base.

### 21.2 Exact asset tests

Assert exact SHA-256 locks for all eight detector assets listed in Section 5.

A byte mismatch must fail the build.

### 21.3 CAPTCHA tests

Assert:

- exact ROI `(300, 200, 650, 350)`;
- 1280×720 requirement for exact path;
- `0.70` primary threshold;
- secondary threshold only on its corresponding path;
- exact assets return `spotify_exact` only when exact path requirements are met;
- fallback cannot claim exact;
- CAPTCHA path contains no solver/Gemini API call or answer injection.

### 21.4 Full-bag tests

Assert:

- `.35` full-bag threshold distinct from `.65` seller threshold;
- all three inventory-full variants are addressable;
- canny path is used where recovered;
- detector does not call MiuMiu directly;
- safe gate remains mandatory.

### 21.5 Dead/disconnect tests

Assert:

- exact DEAD/ONL asset bytes;
- dead match emits `REVIVE_REQUIRED` or equivalent typed event;
- no invented revive click target is introduced;
- disconnect match releases/pauses but does not auto-login;
- detector functions remain side-effect free.

### 21.6 Watchdog lifecycle tests

Assert:

- independent start/stop/generation;
- cached HWND only;
- no window enumeration;
- no combat-key injection;
- no C2 hot-path detector call;
- detector exception isolation;
- typed event emission;
- sell timer ownership resides in watchdog when enabled.

### 21.7 Session-monitor tests

Assert:

- valid session is passive;
- invalid session causes release/stop event before disable-controls bridge;
- network check occurs outside input lock;
- no invented login/license/HWID behavior;
- worker terminates on STOP/generation change.

### 21.8 Protected component tests

Hash/static guards continue protecting:

- C2 timing/focus path;
- MiuMiu seller core;
- PC Alarm core;
- focus parity module;
- launcher executable/updater contract where release packaging requires it.

### 21.9 Windows preflight

GitHub Actions must:

1. download exact public V9.7.0 base;
2. verify protected V9.7 hashes;
3. apply V9.8 overlay;
4. compile and run full tests;
5. run C2/protected-component guards;
6. run real Windows launcher smoke;
7. package Portable/Update artifacts;
8. verify package contents and SHA;
9. upload private preflight artifacts;
10. skip all public release/update steps when `publish=false`.

Public release requires a separate user approval after preflight is green.

## 22. Acceptance criteria

V9.8.0 is implementation-complete only when all of the following are true:

1. all V9.7 regression tests pass;
2. all eight exact detector asset hashes are locked and pass;
3. exact CAPTCHA detector paths use recovered assets/ROI/thresholds and never solve CAPTCHA;
4. full-bag detector supports recovered multi-asset/canny structure with `.35` threshold;
5. exact dead/disconnect detection is active where call geometry is proven;
6. revive action does not invent coordinates or target geometry;
7. watchdog owns detector/event work outside farm hot paths;
8. C2 path contains no watchdog/session/detector scanning and retains recovered timing/focus behavior;
9. safe-place verification remains mandatory before MiuMiu;
10. MiuMiu seller core remains behaviorally unchanged;
11. PC Alarm core remains behaviorally unchanged;
12. session monitor implements only the recovered `check_session -> invalid/KICK -> disable controls/release` semantics;
13. no new license/HWID/login policy is invented;
14. dynamic combo remains unwired without caller evidence;
15. Auto Market All Cure remains out of scope;
16. Windows preflight `publish=false` completes successfully before public release approval;
17. release notes distinguish exact, structural, fallback, and intentionally omitted behavior.

# Nghĩa V9.8.0 — Spotify Exact Detector & Watchdog Recovery Design

## 1. Goal

Build V9.8.0 from the released V9.7.0 line and recover every remaining Spotify subsystem currently supported by direct or high-structural binary evidence **except `session_monitor_worker` and all login/license/session enforcement behavior**, which Nghĩa explicitly does not need.

V9.8.0 scope:

1. exact recovered Spotify detector assets and matching paths for CAPTCHA, dead/revive, online/disconnect, and full-bag;
2. broader `watchdog_worker` recovery, including detector ownership, alarm/event routing, auto-revive where action geometry is evidenced, full-bag/sell ownership, and recovered randomized-sell structure;
3. Auto Market All Cure as an independent opt-in subsystem;
4. dynamic-combo caller recovery and wiring only where direct/high-structural caller evidence identifies the actual farm path;
5. `main_farm_worker` topology recovery only where ownership/call ordering is evidenced strongly enough to avoid speculative scheduler rewrites;
6. preserve exact/current MiuMiu asset bytes and seller core behavior;
7. preserve V9.7 C2 timing/focus and every validated farm-mode path.

Explicitly excluded:

- `session_monitor_worker`;
- `check_session` loops;
- login/license/session-token validation;
- KICK/session-driven `disable_all_controls` behavior;
- automated CAPTCHA solving, Gemini CAPTCHA solving, or CAPTCHA bypass.

CAPTCHA support in Nghĩa remains strictly:

`detect -> pause/release -> PC Alarm / Telegram / status -> wait for user`.

## 3. Source-of-truth hierarchy

Implementation choices follow this order:

1. direct Spotify binary/payload evidence from the verified raw reference;
2. runtime-validated Spotify behavior;
3. high-structural reconstruction from Nuitka constants, names, locals, embedded assets, strings, branch structure, and call ordering;
4. current Nghĩa behavior as a clearly labeled compatibility fallback or Nghĩa extension.

Rules:

- never invent coordinates, thresholds, jitter bounds, sleeps, retry counts, or caller mappings;
- exact embedded bytes may be labeled `spotify_exact` only when byte-validated against the verified Spotify payload;
- an exact asset alone does not make an unknown crop/action path exact;
- a recovered threshold alone does not prove exact detector parity without the correct asset/path;
- dynamic combo is wired only when the actual caller path is evidenced;
- `main_farm_worker` is reconstructed incrementally, never by wholesale scheduler replacement based only on its symbol name;
- C2 remains isolated from speculative global scheduling work.

## 6. Detector architecture

`spotify_detection_parity.py` remains the detector-policy layer and is extended rather than duplicated.

Required result contract remains:

```python
@dataclass(frozen=True)
class SpotifyDetectionResult:
    kind: str
    matched: bool
    score: float | None
    threshold: float | None
    source: str
```

Allowed sources:

- `spotify_exact`;
- `spotify_structural`;
- `nghia_fallback`.

Detector functions must be deterministic for a supplied frame and must never:

- pause the bot;
- play alarms;
- send Telegram messages;
- press keys;
- move/click the mouse;
- enumerate windows;
- call account/session/network APIs.

All side effects remain in watchdog/host action bridges.

## 7. CAPTCHA exact recovery

### 7.1 Direct evidence

Recovered direct constants and assets:

- game size: 1280×720;
- ROI: left `300`, top `200`, width `650`, height `350`;
- primary threshold: `0.70`;
- secondary recovered CAPTCHA threshold: approximately `0.68` on its corresponding path;
- `LIE_B64`;
- `QUESTION_CAPTCHA_1_B64`;
- `QUESTION_CAPTCHA_2_B64`;
- watchdog ownership;
- Spotify binary also contains `process_auto_captcha` and Gemini-related logic.

### 7.2 V9.8 detector policy

At exactly 1280×720:

- use the recovered ROI contract;
- `LIE_B64` may report `spotify_exact` only through its recovered matching path and threshold semantics;
- question-CAPTCHA assets may report `spotify_exact` only through their corresponding recovered paths;
- secondary threshold `~0.68` must never be applied generically to unrelated templates.

At non-1280×720:

- exact Spotify CAPTCHA path is disabled;
- existing Nghĩa detector may continue as `nghia_fallback`;
- scaled ROI behavior must not claim exact parity.

### 7.3 No-solver invariant

V9.8 intentionally does **not** reproduce Spotify's Gemini/AI CAPTCHA solver.

Allowed response:

`detect -> pause/release -> local alarm / Telegram / status -> wait for user`.

Prohibited:

- sending CAPTCHA images to Gemini or another model to solve them;
- generating answers to CAPTCHA challenges;
- typing/clicking an answer automatically;
- automatic retry/bypass of the challenge.

Static/runtime tests must fail if the CAPTCHA watchdog path imports or calls Gemini/Google generative-AI solving APIs.

- a full-bag match emits a sell-request event but cannot directly call MiuMiu;

## 9. Dead detection and auto-revive

Direct/high-confidence evidence includes:

- exact `DEAD_B64`;
- watchdog dead-detection branch strings;
- PyDirectInput mouse movement/click primitives in the dead/revive cluster;
- user-visible revive action equivalent to clicking `Hồi sinh`;
- Telegram dead notification strings.

V9.8 separates detection parity from action parity.

### 9.1 Dead detection

Exact `DEAD_B64` through the recovered detector path may return `spotify_exact`.

### 9.2 Auto-revive action

On dead match, watchdog emits an event equivalent to `REVIVE_REQUIRED`.

Auto-revive becomes active only if implementation-time binary/runtime evidence proves the target geometry or an already-existing validated host action supplies the same target safely.

If coordinates/target geometry remain unresolved, V9.8 must:

- pause/release;
- alert;
- expose `REVIVE_REQUIRED`;
- not invent a click point.

If auto-revive is enabled after evidence is recovered, it must:

- execute through a dedicated serialized host action bridge;
- release farm input before clicking;
- abort on STOP/generation change;
- never run while MiuMiu/market transaction owns input;
- carry an explicit evidence label in diagnostics.

## 11. SpotifyWatchdogWorker V9.8

`SpotifyWatchdogWorker` remains a dedicated worker outside all farm hot paths.

V9.8 responsibilities:

- capture alert frames through existing host capture bridge;
- exact/fallback CAPTCHA checks;
- exact dead detection;
- exact/structural online-disconnect detection;
- exact/structural full-bag detection;
- typed event emission;
- local alarm/Telegram request routing through existing bridges;
- full-bag/timer sell scheduling ownership;
- auto-revive request emission where action evidence is sufficient;
- coordination with safe-place sell gate.

Direct worker evidence includes:

- `watchdog_worker`;
- `watchdog_worker.<locals>.process_auto_captcha`;
- `play_local_alarm`;
- `get_next_sell_delay`;
- sell-timer state such as `last_sell_time` / `next_sell_delay`.

`process_auto_captcha` is **not** reproduced as an automatic solver; V9.8 recovers only detector/alert ownership.

Watchdog must never:

- call `_find_game_window` or `EnumWindows` in its loop;
- refresh focus/HWND ownership itself;
- inject combat keys;
- modify C2 timing;
- run detector work inside C2 Fast Worker;
- invoke MiuMiu before safe-place `READY`;
- solve CAPTCHA;
- invoke any session-monitor/login/license behavior.

## 12. Randomized sell scheduling

Direct evidence establishes that Spotify watchdog owns:

- `last_sell_time`;
- `next_sell_delay`;
- `sell_interval_minutes`;
- `get_next_sell_delay`;
- `random.uniform` usage.

This proves scheduling ownership and randomized-delay structure, but the currently recorded evidence does not yet prove the numeric `random.uniform` bounds.

Required policy:

- watchdog owns the sell timer;
- introduce/test a `get_next_sell_delay` boundary;
- preserve configured `sell_interval_minutes` meaning;
- if exact jitter bounds are recovered during implementation, amend this spec before enabling exact randomized bounds;
- otherwise preserve V9.7 fixed interval as `nghia_fallback` rather than inventing numbers;
- every timer-triggered sale still passes the V9.7 safe-place gate.

## 13. Safe-place and MiuMiu contract

V9.8 preserves the V9.7 transaction gate:

```text
FULL_BAG / TIMER SELL REQUEST
-> pause/serialize farm
-> MOVE_SAFE
-> SETTLE_SAFE
-> VERIFY_SAFE (max 6 observations)
-> READY
-> existing MiuMiu seller
```

If safe verification returns `FAILED`:

- abort/clear the sell request under existing V9.7 rules;
- release owned movement/skill input;
- do not enter MiuMiu;
- return to recovery/farm under existing generation semantics.

MiuMiu seller core remains behaviorally protected. No generic keyboard-only seller fallback may be reintroduced.

## 16. main_farm_worker topology recovery

Spotify contains a dedicated `main_farm_worker` in addition to watchdog/focus workers.

V9.8 attempts deeper recovery, but only evidence-backed ownership/order may change runtime architecture.

Protected strategy:

- do not replace the V9.7 dispatcher wholesale;
- identify non-C2 responsibilities clearly owned by `main_farm_worker`;
- move/wire only those responsibilities with tests proving behavior equivalence;
- keep C2 dedicated fast worker isolated;
- preserve STOP/generation release behavior;
- add no new sleeps/RNG ordering without evidence;
- if the call graph remains incomplete, record evidence and leave the current non-C2 dispatcher intact.

Thus “recover main_farm_worker” means recovering proven ownership/topology, not blindly recreating a four-thread architecture around guessed internals.

## 17. Explicit exclusion: session monitor

Nghĩa V9.8 deliberately does not implement Spotify `session_monitor_worker`.

Do not add or restore:

- `SpotifySessionMonitorWorker`;
- `session_monitor_worker` runtime thread;
- `username -> session_token -> check_session` loops;
- KICK/session-expiry flows;
- session-driven `disable_all_controls` behavior;
- account/license/session-token enforcement;
- re-authentication/re-login behavior derived from Spotify session code.

Tests must assert that V9.8 does not introduce an active session-monitor path.

The Spotify Offline NoLogin wrapper is external scaffolding and is not justification for restoring session enforcement into Nghĩa.

## 18. Concurrency and input ownership

V9.8 introduces more side-effect transactions, so ownership is explicit.

Serialization priority:

1. STOP/generation invalidation;
2. safety/alert release;
3. revive transaction if valid/enabled;
4. safe-place/MiuMiu sell transaction;
5. All Cure market transaction;
6. normal farm input.

Rules:

- detectors never own input;
- watchdog requests actions through host bridges;
- only one side-effect transaction owns mouse/keyboard at a time;
- farm worker releases/pauses before revive/sell/market ownership;
- focus worker owns focus/HWND refresh only;
- no detector enumerates windows;
- no long image/network operation holds the shared input lock;
- C2 timing remains outside watchdog/market transaction logic.

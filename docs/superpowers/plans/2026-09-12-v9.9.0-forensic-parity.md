# Nghia V9.9.0 Forensic Parity Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver V9.9.0 as five independently verified Spotify-forensic parity improvements assembled into one private-preflight release candidate.

**Architecture:** The approved design spans five independent subsystems, so implementation is split into five focused TDD plans plus one integration/release plan. All plans produce files under the same `release_payload/v9.9.0/` overlay; cumulative host/core patches are rebased after each subsystem so the final overlay applies once to the exact public V9.8.1 base.

**Tech Stack:** Python 3.12, pytest, GitHub Actions Windows, PowerShell, existing Nghia overlay/patch release pipeline.

**Spec:** `docs/superpowers/specs/2026-09-12-v9.9.0-forensic-parity-design.md`

## Global Constraints

- Branch: `release-v9.9.0-forensic-parity`.
- Base: exact public V9.8.1 Portable SHA-256 `e36350ab7e8285f3e7f0c4d1cc80aee9c88d4c5927249bb11dcc40b989694d46`.
- Evidence labels are exactly `direct`, `high_structural`, or `nghia_fallback`; High-structural behavior is never relabeled Direct.
- No `session_monitor_worker`, `check_session`, login/license/session enforcement, KICK-driven disabling, CAPTCHA solver, Gemini/generative AI, or automated CAPTCHA answering.
- V9.8.1 C1/C2/B1/B3 shared hold-combo semantics remain protected.
- Dynamic Combo remains dormant/evidence-gated; Pirate Laptop remains out of scope.
- Public publishing is forbidden until successful private preflight is reported and the user explicitly says `publish V9.9.0`.

## Cross-plan Ownership Contracts

- **Disconnect:** `ONL_B64` identity and threshold `0.95` are Direct. The complete frame/caller path remains `high_structural`; detector results must therefore use structural source labeling.
- **Sell timer:** watchdog is sole timer owner. Timer maturity latches `sell_due_pending` and raises one host event. Main-farm dispatch uses a Nghia-only `spotify_sell_inflight` guard to prevent duplicate thread launches: dispatch clears the host event and sets inflight; confirmed seller success calls `notify_sell_completed` and clears inflight; seller failure/cancel clears inflight, re-sets `spotify_sell_timer_event`, and leaves watchdog pending/timing unchanged. This inflight/re-arm guard is `nghia_fallback`, not Spotify evidence.
- **Main farm:** orchestrator owns order only. It does not generate sell delays, mark sales complete, create worker threads, or own focus/watchdog scanning.
- **All Cure:** generic core executor is data-driven. Assets READY alone never bypasses workflow evidence. Any unresolved execution field leaves workflow BLOCKED; future evidence JSON can fill those fields without rewriting executor code.

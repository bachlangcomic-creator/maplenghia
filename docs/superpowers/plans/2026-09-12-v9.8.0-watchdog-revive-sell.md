# Nghĩa V9.8.0 Watchdog, Revive & Sell Scheduling Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Expand the V9.7 watchdog to own evidence-backed detector events, alert/revive requests, and sell scheduling while preserving C2 isolation and the safe-place MiuMiu gate.

**Architecture:** `SpotifyWatchdogWorker` remains side-effect-light and consumes cached HWND plus host capture/scan bridges. It emits typed events; the host performs serialized safety actions after releasing farm ownership. Revive click/action and randomized sell jitter are gated by recovered evidence and remain disabled/fallback when geometry/bounds are not proven.

**Tech Stack:** Python 3.12, threading, pytest, existing Maple host/input bridges, V9.8 detector modules from Plan 1.

**Spec:** `docs/superpowers/specs/2026-09-12-v9.8.0-exact-detector-watchdog-recovery-design.md`

## Global Constraints

- Requires completion of `2026-09-12-v9.8.0-exact-assets-detectors.md`.
- Watchdog must use `_spotify_cached_game_hwnd()` only; no `_find_game_window` or `EnumWindows` in its loop.
- Watchdog must never press combat keys or alter C2 timing.
- CAPTCHA is alert-only; no automatic solver or answer input.
- MiuMiu starts only after V9.7 safe-place returns `READY`.
- Missing revive target/click geometry disables auto-revive action rather than inventing coordinates.
- Exact sell jitter bounds must not be invented; V9.7 fixed interval remains fallback until bounds are directly recovered and the spec is amended.
- No session-monitor/login/license/session code.
